# Changeset Fragments

Skill for writing Changeset fragments in the quiltt-sdks monorepo. Changesets
use the standard [Changesets CLI](https://github.com/changesets/changesets)
with a fixed versioning group — all 8 packages (`core`, `react`, `vue`,
`react-native`, `capacitor`, `android`, `flutter`, `ios`) version together.

---

## Location

Fragments live in `.changeset/*.md` at the repo root. Generated by:

```bash
pnpm changeset
```

This starts an interactive prompt to select the bump type and write the
summary. The generated file is named by Changesets (a random slug like
`twelve-kiwis-film.md`). Commit the file alongside your code changes.

**Do not hand-create a `.changeset/*.md` file** — always run `pnpm changeset`
and fill in the summary at the interactive prompt.

---

## Bump Types

All 8 packages version together (fixed group), so you only need to select
**one** affected package. The selected bump type applies to all:

| Type | When | Example |
|------|------|---------|
| `patch` | Bug fixes, minor updates, non-breaking improvements | `1.0.0 → 1.0.1` |
| `minor` | New features, backwards-compatible changes | `1.0.0 → 1.1.0` |
| `major` | Breaking changes | `1.0.0 → 2.0.0` |

---

## Front Matter

Changesets auto-generates the YAML front matter. Never edit it manually.
The front matter looks like:

```yaml
---
"@quiltt/core": patch
---
```

Select **any one** package — the fixed group bumps all 8 regardless.

---

## Writing the Summary

The summary is the body text below the front matter. It becomes the changelog
entry in each package's `CHANGELOG.md`.

### Audience

Write for **developers integrating with the Quiltt SDKs**. Describe
**observable behaviour** — what the developer can now do, what works
differently, or what was broken that now works. Focus on the outcome, not
the implementation details.

### Structure

One or two paragraphs. Start with the most important thing the change does.
Include specific API names, component names, hook names, and types where
relevant.

### Style Rules

- **Imperative mood**: "Add support for…", "Fix issue where…", "Remove deprecated…"
- **Be specific**: name the package, component, hook, or type affected
- **Describe behaviour, not implementation**: "Fix `fetchWithRetry` returning `undefined` on empty responses" not "Update error handling in fetchWithRetry to check response body length"
- **No trailing period** on single-sentence summaries
- **Reference breaking changes clearly**: prefix with `**Breaking**`

### Examples

**Patch — bug fix:**

```markdown
Mark `FetchResponse<T>.data` as `T | null` to match runtime reality — `fetchWithRetry` already returns `null` when `response.json()` fails (empty or malformed bodies).

Add optional chaining guards across `react` and `vue` session, institutions, and resolvable hooks to prevent `Cannot read properties of null` crashes.
```

**Minor — new feature:**

```markdown
Add `useAccountBalance` hook to `@quiltt/react` for real-time balance updates. Returns current balance, available credit, and last-updated timestamp for the given account ID.
```

**Major — breaking change:**

```markdown
**Breaking** Remove deprecated `authenticate` prop from `QuilttProvider`. Use the `token` prop with `useQuilttSession().importSession()` instead.
```

### What to Omit

- Template comments or placeholder text
- Issue/ticket numbers in the summary body (they belong in the PR description and commit message)
- Vague entries like "Misc cleanups", "Bug fixes", "Minor improvements"
- Internal-only refactors, test additions, or CI changes that don't affect the public API or observable behaviour
- Implementation details that don't affect what the developer experiences

### One Change per Changeset

A changeset should describe one logical change. If a PR ships two unrelated
changes (e.g. a feature *and* a separate bug fix in a different area), create
two changeset files:

```bash
pnpm changeset   # first change
pnpm changeset   # second change
```

This produces two `.changeset/*.md` files. Their summaries are concatenated
into the release changelog.

## Full Workflow

1. Make code changes on a feature branch
2. Run `pnpm changeset`
3. Select any one package (e.g. `@quiltt/core`) — all 8 will bump together
4. Choose the bump type (`patch` / `minor` / `major`)
5. Write the summary following the style guide above
6. Commit the generated `.changeset/*.md` file with your code changes
7. Push and open a PR
